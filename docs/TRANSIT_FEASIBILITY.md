# Ehime Mobility Resilience Lab

## Transit / Accessibility Feasibility

### A0 Agent E deliverable

- 調査基準日：2026年8月22日（JST）
- 対象：愛媛県内のGTFS、GTFS-JP、GTFS-Realtime、鉄道、フェリー、公共交通アクセシビリティ
- 目的：A1で実際に着手できる公共交通分析の範囲を確定する
- 制約：A0ではコード実装、GTFS生データのリポジトリ登録、Phase Bデータの取得・加工を行わない

## 1. 結論

Phase Aの公共交通アクセシビリティ分析は実現可能である。

ただし、2026年8月22日時点で「愛媛県内の全公共交通をGTFSで網羅できる」ことは確認できていない。
したがって、A1の開始時点では、公共交通の提供範囲をデータセット単位で表示し、GTFSが確認できない交通を存在するものとして補完しない。

現時点での現実的な開始範囲は次のとおりである。

1. 伊予鉄バスの静的GTFS-JPを、認証・利用条件確認後に分析入力とする
2. 大洲市「ぐるりんおおず」の静的GTFSを、公式公開ファイルとCC BY 4.0条件を確認したうえで利用する
3. 宇和島運輸・オレンジフェリーのGTFSを、ODPTの認証・利用条件確認後に航路候補として利用する
4. 伊予市「あいくる」は、現時点では停留所座標データとして扱い、時刻表付きアクセシビリティ計算の入力とは扱わない
5. JR四国および伊予鉄道の鉄道ダイヤGTFSは、今回の確認範囲では未確認とする
6. GTFSが未確認の鉄道について、OSMや国土数値情報の鉄道形状だけから運行ダイヤを生成しない

従って、A1の第一段階は「GTFSが実際に計算へ入る伊予鉄バスを中心にした、部分カバレッジの公共交通アクセシビリティ」である。
県全域を対象とする場合も、結果にはフィードカバレッジ、未収載事業者、データ基準日、計算対象外モードを明示する。

## 2. 調査結果の読み方

本書では、次の用語を区別する。

| 表記 | 意味 |
| --- | --- |
| confirmed | 公式提供元の公開ページまたは公式カタログで、対象データの存在を確認した |
| available after access control | データの存在は確認したが、利用者登録、APIキー、開発者規約または個別条件の確認が必要 |
| partially available | 交通の一部情報はあるが、時刻表付きGTFSとしては不足している |
| not confirmed | 調査範囲では対象データを確認できなかった。不存在を意味しない |
| unavailable for calculation | 現在確認できる資料だけでは、当該モードの時刻依存アクセシビリティを計算できない |
| out of scope | Phase AまたはA1では計算対象にしない |

「not confirmed」を「存在しない」と表示してはならない。
「unavailable for calculation」を交通サービスの不存在や運休と表示してはならない。

### 3.2 鉄道の状況

JR四国は公式サイトで駅情報、発車時刻表、路線別の案内を提供している。
伊予鉄道も公式サイトで市内電車・郊外電車の路線図と時刻表検索を提供している。

一方、今回の調査では、JR四国または伊予鉄道の現行の旅客ダイヤを、公開利用条件付きのダウンロード可能なGTFSまたはGTFS-JPとして確認できなかった。
この結果は「鉄道GTFSが存在しない」という意味ではなく、A1の入力として利用できる状態を確認できていないという意味である。

鉄道の扱いは次のとおりとする。

- JR四国の公式Web時刻表をスクレイピングしてGTFS化しない
- 伊予鉄道のPDF路線図・Web時刻表からダイヤを推測してGTFS化しない
- 国土数値情報やOSMの鉄道形状を、鉄道の運行時刻・運行頻度・所要時間の代替にしない
- 鉄道GTFSが提供され、ライセンス、基準日、運行カレンダー、駅ID、停車時刻を検証できた場合にだけ、鉄道アクセシビリティを有効化する
- 鉄道形状だけを表示する場合は、スケジュール計算とは別の「参考形状」レイヤーとして扱う

### 3.3 その他のバス・デマンド交通

愛媛県内には、市町村コミュニティバス、デマンドタクシー、事業者路線等が存在する可能性がある。
しかし、全事業者について現行GTFSの提供状況と利用条件を確認したわけではない。

したがって、次の資料だけから時刻依存アクセシビリティを作成しない。

- PDF時刻表のみ
- 路線図画像のみ
- 停留所一覧のみ
- 広報紙の運行案内のみ
- 予約型交通の運行区域だけを示す資料

これらは将来のデータ取得候補としてインベントリに記録する。
正式なGTFSまたは同等の機械可読な運行データが取得できるまで、A1の計算結果には含めない。

### 3.4 GTFSデータリポジトリの補助確認

GTFSデータリポジトリの愛媛県、都道府県コード38、2026年8月22日を対象とした確認を行った。
この確認では、APIの当該検索結果は空配列であった。

ただし、これは次の理由から全県のGTFS不存在を意味しない。

- 事業者が別の配信基盤を使っている可能性がある
- APIの検索条件や掲載方法によって結果が変わる可能性がある
- ODPTや自治体公式ページで直接配信されるフィードは別経路である
- フィードの有効期間や登録状態が検索日によって変わる

従って、GTFSデータリポジトリは発見用の補助情報とし、採用判定は提供元の公式ページ、個別ライセンス、フィード本体の検証によって行う。

## 5. GTFS入力の必須要件

### 5.1 最低限解釈するファイル

A1の静的アクセシビリティ計算では、次のファイルを必須または条件付き必須として扱う。

| ファイル | 扱い | 主な用途 |
| --- | --- | --- |
| agency.txt | 必須 | 事業者、タイムゾーン、連絡先 |
| stops.txt | 必須 | 停留所・駅・港の位置、名称、階層 |
| routes.txt | 必須 | 路線、交通モード、表示名、route_type |
| trips.txt | 必須 | 路線とサービス日の便の関係 |
| stop_times.txt | 必須 | 便ごとの停車順、到着時刻、出発時刻 |
| calendar.txt | 条件付き必須 | 曜日パターンと有効期間 |
| calendar_dates.txt | 条件付き必須 | 祝日、臨時便、運休等の例外 |
| shapes.txt | 任意 | 車両が走行する線形の表示と区間対応 |
| feed_info.txt | 推奨 | フィード発行者、フィード期間、バージョン |
| transfers.txt | 任意だが重要 | 乗換時間や乗換制約 |
| frequencies.txt | 任意 | 時刻表ではなく運行間隔で表す便 |

GTFSの仕様上、運行日はcalendar.txtとcalendar_dates.txtを組み合わせて決定できる。
特定の日の臨時運行や運休を反映せずに「平日ダイヤ」とだけ扱うことは禁止する。

### 5.2 時刻の処理

GTFSの時刻は、日付をまたぐ運行を24時以降の値で表すことがある。
たとえば25時10分は翌日午前1時10分ではあるが、サービス日上は同一便の連続した時刻として扱う。

A1の実装要件は次のとおりである。

- 24時を超える時刻を受け付ける
- 時刻を単純な時刻型だけで処理しない
- サービス日、実日付、タイムゾーンを別フィールドで保持する
- 到着時刻と出発時刻の順序を検証する
- 同一便のstop_sequenceが単調増加することを検証する
- calendar.txtの期間外の便を運行便として扱わない
- calendar_dates.txtのexception_type 1を追加、2を削除として反映する
- フィードの有効期間外を「運休」と表示せず、「入力フィード対象外」と表示する

## 6. shapes.txtがない場合の扱い

shapes.txtはGTFS上の任意ファイルである。
従って、形状がないフィードを即座に無効とはしないが、地図上の線を推定線形として明示する。

### 6.1 優先順位

形状の採用優先順位は次のとおりとする。

1. 公式GTFSのshapes.txt
2. 公式に提供された経路形状
3. stop_sequenceに沿って停留所座標を結んだstop polyline
4. フェリーの港間を結ぶ表示用のwater chord
5. 形状なし

### 6.2 stop polyline

shapes.txtがない場合、連続する停留所の座標を接続した線を生成できる。
ただし、この線は実際の道路走行軌跡ではなく、停留所間を直線で補間した表示用の近似である。

stop polylineを使う場合は、次の表示を付ける。

- 形状区分：BまたはCの加工・近似
- 表示名：停留所接続による近似線
- 注意書き：実際の走行経路、道路中心線、災害時の通行可能経路を示さない

stop polylineを道路リンクの閉鎖判定に自動利用してはならない。
道路障害とバス運休を連動させるには、公式形状、道路へのマップマッチング、またはユーザーが設定した路線・区間停止条件が必要である。

### 6.3 フェリー形状

フェリーについて、港の位置とstop_timesがある場合は、発着時刻に基づく時刻依存ネットワークを作成できる。
ただし、港間の単純な直線は航路、航行可能水域、実際の船舶軌跡を示さない。

従って、フェリーの港間線は次のどちらかとして扱う。

- 公式shapeがある場合：公式形状
- 公式shapeがない場合：表示用の港間接続線

後者では、線形から海上距離、航行時間、災害時の航路可否を逆算しない。

### 6.4 形状なしで計算可能な範囲

形状がなくても、停留所、便、stop_times、運行日が正しく存在すれば、停留所間の時刻依存アクセシビリティは計算できる。
ただし、地図上の走行線表示、道路閉鎖との空間的な交差判定、路線区間の正確な位置選択は制限される。

UIでは、計算可能性と地図形状の精度を別々に表示する。

## 7. 公共交通ネットワークの設計

### 7.1 論理ネットワーク

GTFSから、次の論理エッジを生成する。

- 停留所への徒歩アクセス
- 乗車待ち
- 車両・列車・船舶への乗車
- 同一便の停留所間移動
- 降車
- 乗換
- 停留所から目的地への徒歩アクセス

停留所ID、route_id、trip_id、service_idは、複数フィードを統合しても衝突しないよう、フィードIDを名前空間として付与する。

推奨形式は次のとおりである。

- feed_id: providerとfeedの論理識別子
- stop_key: feed_idとstop_idの組
- route_key: feed_idとroute_idの組
- trip_key: feed_idとtrip_idの組
- service_key: feed_idとservice_idの組

ローカルIDだけを全国・県内統合キーとして使わない。

### 7.2 交通モード

GTFSのroute_typeだけで運行実態を完全に表現できるとは限らない。
A1では、少なくとも次のモード分類を保持する。

- bus
- rail
- tram
- ferry
- other

モード分類の根拠はroute_type、agency、route_name、データ提供元の説明を保存する。
文字列の路線名だけで鉄道やフェリーを推定しない。

### 7.3 乗換

乗換は、単純なゼロ分接続としない。
次の情報を使い、未提供の場合は明示的な既定値を設定する。

- transfers.txt
- stop_idとparent_station
- 駅・港の乗換施設情報
- 最小乗換時間
- 徒歩接続距離
- 同一停留所名だが異なるstop_idの扱い

乗換時間の既定値を使用した場合は、推定・仮定区分Dまたはモデル入力として記録する。

## 8. Routing / Accessibilityエンジン候補

### 8.1 比較

| 候補 | 特徴 | 長所 | 制約 | A1判定 |
| --- | --- | --- | --- | --- |
| r5py / R5 | OSMとGTFSを使うPythonインターフェース。徒歩、自転車、公共交通、自動車の旅行時間行列とアクセシビリティ向け | Python分析層に組み込みやすい。多対多、出発時間帯、公共交通を扱える | JVM、OSM PBF、GTFS、環境再現の固定が必要。バージョン固定が必要 | 第一候補 |
| OpenTripPlanner 2 | OSM・GTFSを用いるマルチモーダル経路計画サーバ | 乗換、徒歩、公共交通、GTFS-RT、API、可視化連携が成熟 | Javaサービス運用、グラフ構築、設定・運用負荷が大きい | A1後半または将来候補 |
| NetworkX | 汎用グラフと最短路 | 監査用の小規模グラフ、障害前後比較、単体テストに適する | 時刻依存GTFS、乗換、出発時刻分布を自動処理する専用機能ではない | 補助・検証用 |
| AequilibraE | QGIS・交通計画・配分との統合を意識した分析基盤 | 交通量配分と公共交通データの接続候補 | A1の公共交通アクセシビリティだけには重い | A3以降で再評価 |
| ブラウザ内独自実装 | JSON等を配信してJavaScriptで計算 | GitHub Pagesだけで動かせる | 大規模多対多、時刻依存、再現性、性能、入力品質管理が難しい | 表示・軽量再生に限定 |

### 8.2 推奨方針

A1の分析エンジンは、第一候補をr5pyとする。
r5pyはOSMの道路・徒歩ネットワークとGTFSを組み合わせ、出発時刻を考慮した旅行時間行列とアクセシビリティ計算を行えるためである。

ただし、A0段階でr5pyの採用を無条件に確定しない。
次の小規模実証をA1の最初のゲートとする。

1. 伊予鉄バスの認証済み静的GTFSを読み込める
2. 大洲市の公開GTFSを読み込める
3. 代表的な人口ゾーンと施設を起点・終点にできる
4. 平日・休日・指定日時の結果が変わる
5. フィードの有効期間外を誤って計算しない
6. ルート停止条件を入力すると、計算結果が変化する
7. 生成物にデータ版、モデル版、パラメータ、Git SHAを付与できる

この実証が失敗した場合は、OpenTripPlanner 2を分析サービス候補として再評価する。
GitHub Pagesにはいずれのエンジンも配置せず、計算済みの静的成果物だけを公開する。

### 8.3 ルーティングの段階

#### A1-Transit-1：GTFSの検証と時刻依存停留所ネットワーク

- 停留所、路線、便、stop_times、calendarを解釈
- 指定日・指定時刻の到達可能性を計算
- shapesは表示品質と区間選択に利用
- 静的GTFSを中心にする

#### A1-Transit-2：OSM徒歩接続を含む公共交通アクセシビリティ

- 人口メッシュまたは人口ゾーンを最寄り停留所へ接続
- 目的地候補を病院、災害拠点病院、行政、都市中心部等に接続
- 30分、60分、90分の閾値を計算
- 徒歩接続距離、乗換時間、出発時間帯を保存

#### A1-Transit-3：ユーザー設定の公共交通停止

- route停止
- trip停止
- stop-to-stopの論理区間停止
- ferry route停止
- railは入力フィードがある場合のみ有効化

道路通行止めによって、バスが自動的に運休するような連動はA1の既定機能としない。
道路とバスの空間連動を行う場合は、路線形状と道路リンクの対応精度を検証した別機能として実装する。

## 9. Accessibility指標

### 9.1 基本指標

GTFSカバレッジのあるモードについて、最低限次を計算する。

- 30分以内に到達できる目的地数
- 60分以内に到達できる目的地数
- 90分以内に到達できる目的地数
- 30分、60分、90分圏に含まれる人口
- 到達不能人口
- 目的地までの平均旅行時間
- 公共交通アクセシビリティ損失
- Essential Access Recovery Rate

ここでいう人口は、対象人口ゾーンの人口を集計したモデル値である。
個人の移動履歴や実際の利用者数ではない。

### 9.2 Before / After

シナリオ比較では、同一の次元、同一の人口ゾーン、同一の目的地集合、同一の出発日時条件を使う。

アクセシビリティ損失の基本表示は次のとおりとする。

Accessibility Loss
= Baseline accessibility minus Scenario accessibility

率で表示する場合は、基準値が0のときに無理な除算をしない。
基準値が0または計算対象外の場合は、率を「計算対象外」と表示する。

### 9.3 出発時間帯

公共交通は出発時刻によって待ち時間が変わる。
特に本数の少ない地方部では、単一の出発時刻だけで代表値を作ると結論が不安定になる。

A1では、次の条件を保存する。

- service_date
- day_type
- departure_start
- departure_end
- departure_sampling_interval
- percentileまたは集約方法
- max_travel_time
- walking_speed
- transfer_penalty

既定値を設定する場合も、行政利用者が変更可能なパラメータとして表示する。

### 9.4 カバレッジと未計算

鉄道GTFSがない地域や、時刻表のないコミュニティ交通について、公共交通利用不能を意味する0分・0人口を出力してはならない。

出力を次の状態に分ける。

- computed：入力フィードと条件がそろい、計算済み
- partial_coverage：一部の事業者またはモードだけで計算
- input_required：GTFS、施設、人口などの入力が不足
- out_of_scope：A1対象外
- not_computed：計算を実行していない

UIには、計算値と未計算理由を同時に表示する。

## 10. Transit disruptionの実現可能性

### 10.1 route停止

GTFSのroute_idに対応する全tripを停止させるモデルは、静的GTFSだけで実装可能である。
伊予鉄バス、コミュニティバス、GTFSとして提供されるフェリーに適用できる。

ただし、「この路線が災害で停止する」という予測ではなく、「ユーザーがこの路線を停止させた場合」のStress Testである。

### 10.2 stop-to-stop区間停止

stop_sequenceに基づく連続停留所間エッジを停止させるモデルは実装可能である。
shapesがない場合でも論理ネットワーク上は扱える。

ただし、地図上の区間位置を正確に示せない場合がある。
その場合、UIは「停留所間の論理区間」と表示し、道路上の正確な閉鎖区間と誤認させない。

### 10.3 rail segment停止

鉄道の時刻依存GTFSが取得できた場合は、rail route、trip、stop-to-stop区間を同じ方式で停止できる。
鉄道GTFSがない状態で、駅間線形だけを使って鉄道区間停止の所要時間影響を計算しない。

### 10.4 ferry route停止

フェリーGTFSにroute、trip、stop_timesが含まれ、港のstopが確認できれば、航路停止、港停止、便停止を計算できる。
航路の幾何形状がない場合も、港間の時刻依存接続は計算できるが、海上経路の線は表示用近似にとどめる。

### 10.5 道路障害との関係

バスが道路を走ることは事実だが、GTFSの形状とOSM道路リンクの対応がない状態で、任意の道路リンク停止からバス運休を自動推論してはならない。

A1での安全な順序は次のとおりとする。

1. 公共交通routeまたは論理区間をユーザーが停止する
2. 公共交通アクセシビリティを再計算する
3. 後工程で、公式shapeと道路リンクの対応を検証する
4. 検証済みの対応だけを、道路障害から公共交通影響へ接続する

## 11. GTFS-Realtimeの扱い

### 11.1 A1で必須にしない理由

本プロダクトの中心は、平時に交通ネットワークの障害条件を設定する静的Stress Testである。
GTFS-Realtimeは、現在位置、遅延、警報などの運行中情報を表すため、平常時の基準ネットワークの再現には必須ではない。

A1では次の方針とする。

- 静的GTFSを基準ネットワークとする
- GTFS-Realtimeは任意の入力拡張とする
- GTFS-RealtimeをGitHub Pagesへ常時プロキシしない
- APIキー、取得日時、データ鮮度、利用条件を別管理する
- リアルタイム情報を過去シナリオの再現結果と混ぜない
- GTFS-Realtimeが取得できないことを「運行なし」と表示しない

### 11.2 将来の用途

利用条件が確認された場合、GTFS-Realtimeは次の用途に限定して検討する。

- 静的GTFSとの整合性確認
- 取得時点の遅延・運行警報の参考表示
- フィード品質監視
- 事業者データ更新の検知

リアルタイムデータを利用した「災害時実績予測」や、未提供情報の補完には利用しない。

## 12. データ品質・検証項目

A1のTransit QAでは、少なくとも次を検証する。

### 構造

- 必須ファイルの有無
- UTF-8または指定エンコーディングの読込
- ヘッダー重複
- 主キー重複
- 空行・不正な引用符
- 緯度経度の範囲
- stop_sequenceの一意性と順序

### 参照整合性

- trips.route_idがroutesに存在する
- trips.service_idがcalendarまたはcalendar_datesに存在する
- stop_times.trip_idがtripsに存在する
- stop_times.stop_idがstopsに存在する
- shapes.shape_idがtripsから参照される場合に存在する
- calendar_datesのservice_idが正しく解決できる

### 時刻・日付

- 到着時刻と出発時刻
- 24時超の時刻
- サービス期間
- 祝日・臨時便・運休
- フィード有効期間
- タイムゾーン

### 空間

- stop_lat、stop_lonの範囲
- 同一停留所の重複
- parent_stationの関係
- shapeと停留所の離れ
- フェリー港と海域の整合性は、単純な地理判定だけで運休を決めない

### 内容

- 路線ごとの便数
- 運行日の有無
- 片方向だけの便
- ループ路線
- 学休日・季節運行
- stop_timesの欠損
- 乗降不可停留所
- frequencyで表された便

検証失敗時はフィードをactiveに切り替えず、candidateまたはrejectedとして保存する。

## 13. ライセンス・公開方針

### 13.1 伊予鉄バス、宇和島運輸、オレンジフェリー

ODPTのデータセットページでは、公共交通オープンデータ基本ライセンスと個別利用条件の確認が求められている。
生ZIP、GTFS-Realtimeの長期キャッシュ、復元可能な派生データを、条件確認なしにGitHubへcommitしない。

A1では次のメタデータだけを先に管理する。

- provider
- dataset title
- source URL
- feed version
- reference date
- downloaded_at
- checksum
- license URL
- terms acceptance status
- redistribution status
- transformation status
- public distribution status

条件確認後に公開可能と判断された派生成果物だけを、Web公開用に出力する。

### 13.2 大洲市

大洲市の公式ページでは、ぐるりんおおずのデータについてCC BY 4.0を確認できる。
出典表示、改変表示、取得日、フィードバージョンを付ける。
ファイル本体を取り込む場合は、公式リンク先の内容とライセンス表示も保存・確認する。

### 13.3 伊予市「あいくる」

伊予市の公式ページでは、停留所座標データをGTFSデータとして公開し、特段の利用制限を設けない旨を確認できる。
ただし、停留所座標データだけで時刻依存の公共交通アクセシビリティを計算できるわけではない。

## 14. A1の現実的な着手順

A1開始時は、次の順序を守る。

### A1-T0：入力確定

- ODPT開発者登録、APIキー、規約同意を確認
- 伊予鉄バス静的GTFSを取得
- 取得日、フィード有効期間、checksumを記録
- 大洲市GTFSを取得し、CC BY 4.0表示を確認
- フェリーGTFSの利用条件を確認
- 鉄道GTFSは引き続き未確認として登録

### A1-T1：フィード検証

- 必須ファイルを検証
- calendarとcalendar_datesを評価
- 代表日で有効便数を確認
- shapesの有無と品質を確認
- stop、route、tripの件数を保存
- フィードごとにカバレッジレポートを出力

### A1-T2：伊予鉄バスの実計算

- 伊予鉄バスのGTFSを実際の計算入力にする
- 停留所、路線、便、stop_timesから時刻依存ネットワークを構成
- OSM徒歩ネットワークと人口ゾーンを接続
- 病院、災害拠点病院、行政、都市中心部等を目的地にする
- 平日・休日・指定日時で30分、60分、90分圏を計算
- すべての結果にデータ版と計算条件を付ける

### A1-T3：障害条件

- route停止
- stop-to-stop論理区間停止
- ferry route停止
- rail停止は鉄道GTFS取得後のみ
- Before / Afterの人口、到達性、平均旅行時間を比較

### A1-T4：Web公開用出力

- 計算済み結果をJSON、GeoJSONまたはParquet等へ出力
- GitHub Pagesでは静的結果を切り替える
- 未計算、部分カバレッジ、入力待ちを明示する
- GTFS生データの公開可否を満たさない場合は、フィード本体を配信しない

## 15. A1の完了条件

A1で公共交通部分を完了扱いにするには、次を満たす。

- 実際に取得したGTFSを計算入力にしている
- 地図に線を表示するだけでなく、stop_timesと運行日を計算に使用している
- GTFSの有効期間と指定日を検証している
- calendar_datesの例外を反映している
- 24時超の時刻を処理している
- shapesあり・なしの両方をテストしている
- feed_idを用いたID名前空間衝突対策がある
- 30分、60分、90分のアクセシビリティを出力している
- route停止または論理区間停止で結果が変化する
- 結果がpartial_coverageであることをUIに表示している
- 鉄道GTFS未確認を鉄道運休や交通不存在と誤表示していない
- GTFS-Realtimeを静的基準値と混同していない
- 使用データ、版、取得日時、ライセンス、モデル版が追跡できる
- 生データの公開条件を満たさないフィードをGitHub Pagesに配信していない

## 17. A0での最終判定

### 判定：条件付きPASS

公共交通を中心とするPhase Aの設計は、伊予鉄バスの実データを使ってA1を開始できるため、実現可能である。

ただし、次の主張は現時点で禁止する。

- 愛媛県全域の公共交通をGTFSで網羅している
- JR四国・伊予鉄道の旅客ダイヤをGTFSで計算している
- GTFS未確認地域を公共交通が存在しない地域とみなす
- GTFS-Realtimeがないことを運休とみなす
- OSMや鉄道形状からダイヤを推定した
- shapesの直線補間を実走行経路と表示する
- 道路閉鎖からバス運休を自動的に断定する

A1は、まず「伊予鉄バスの静的GTFSを実計算へ投入し、時刻・運行日・停留所・人口・施設を用いたアクセシビリティ結果を出す」ことから開始する。
その後、公開条件を満たす大洲市、フェリー、その他のGTFSを段階的に追加する。
鉄道は、公式に利用可能なGTFSまたは同等の機械可読データが確認されるまで、参考形状と時刻依存計算を分離して扱う。

# Ehime Mobility Resilience Lab UX設計

## 文書の位置付け

本書は、Milestone A0におけるAgent Fの成果物である。

対象は、コーディング経験やGIS専用ソフトの操作経験を前提としない愛媛県職員である。

本書は、Public LayerとData Update Centerの情報設計を定める。

完成版UIの実装、画面の高忠実度デザイン、ブラウザ上の再計算エンジンは対象にしない。

本書の設計は、docs/SPECIFICATION.mdの次の原則に従う。

- 公共交通レジリエンスを中心に置く。
- 防災用途を主要な利用目的とする。
- Phase Aを単独で成立させる。
- Phase Bの地震被害想定GISを許諾取得前に扱わない。
- 公式値、公式統計の加工値、モデル推計値、ユーザー仮定を区別する。
- 実被害予測ではなく、交通ネットワークのStress Testとして表示する。
- 重い計算はAnalysis Layerで行い、Public Layerは静的成果物を表示する。

## 1. UXの対象と前提

### 1.1 主利用者

主利用者は、愛媛県の防災危機管理部門、交通政策部門、道路管理部門、公共交通事業者、物流および港湾関係部門の職員である。

利用者は、分析結果を閲覧するだけでなく、会議や内部検討で次の問いに答える必要がある。

- どの交通機能を止めたのか。
- その設定は公式情報か、モデル値か、ユーザーが置いた仮定か。
- どの地域、人口、公共交通利用者、物流拠点に影響が出たのか。
- どの数値が計算済みで、どの数値が未計算なのか。
- どのデータ版とモデル版から結果を作ったのか。
- 障害を復旧させた場合に、どの指標がどの程度戻るのか。
- 別の職員が同じ条件で結果を再現できるか。

### 1.2 初心者向けの操作原則

画面上の基本操作は、次の五段階に固定する。

1. 平常時を見る。
2. 止めてみる。
3. 何が困るかを確認する。
4. どう戻すかを試す。
5. どこが重要かを比較する。

利用者に最初から道路グラフ、OD、BPR、IPFなどの専門用語を要求しない。

専門用語が必要な場合は、画面上に短い説明を置き、詳細な定義と計算条件を説明パネルから確認できるようにする。

### 1.3 UIで使う言葉

画面の主語は「システム」ではなく「交通ネットワーク」または「設定したシナリオ」とする。

次の表現は使わない。

- 被害が発生する。
- 地域が確実に孤立する。
- 交通量を正確に予測する。
- 住民が何人被災する。
- 物流が停止する。

次のように、入力条件とモデル結果を明記する。

- 設定したリンクが使えない場合の計算結果。
- 指定条件下で旅行時間が増加した人口。
- 計算上、指定目的地へ到達できないゾーン。
- モデル配分された交通量。
- 指定した物流拠点への到達時間変化。

## 2. 情報設計の全体構成

### 2.1 Public Layerの役割

Public Layerは、GitHub Pagesから配信する静的な閲覧層である。

地図上でシナリオを選択し、事前計算済み結果を比較する操作を提供する。

ブラウザだけで計算できないシナリオは、計算結果を作成せず、未計算理由と次の手順を表示する。

### 2.2 Public Layerの主要領域

| 領域 | 利用者が確認する内容 | 主な操作 |
|---|---|---|
| ヘッダー | 現在のシナリオ、基準日、データ状態、画面モード | シナリオ変更、データ説明の表示 |
| 目的地ナビゲーション | 平常時、停止、影響、復旧、重要リンクの順序 | 五段階の移動 |
| 地図 | 道路、公共交通、人口、施設、影響リンク | 表示切替、リンク選択、詳細表示 |
| 指標パネル | 人口、公共交通、交通、物流、救援物流の変化 | Before / After切替 |
| モード選択 | PEOPLE、TRANSIT、TRAFFIC、LOGISTICS、RELIEF | 表示テーマの切替 |
| 説明パネル | データ版、モデル、パラメータ、区分、制約 | Provenanceの確認 |
| シナリオ一覧 | プリセット、保存済み、未計算のシナリオ | 選択、複製、再計算要求 |

五つの表示モードは別アプリとして分けない。

モードを切り替えても、現在のシナリオ、基準時点、選択リンク、データ版、結果版を保持する。

### 2.3 モードごとの主な問い

| モード | 主な問い | 代表指標 | 主な注意書き |
|---|---|---|---|
| PEOPLE | 人の到達性はどの地域で変わるか | 到達可能人口、到達不能人口、平均旅行時間、30分、60分、90分圏 | 人口への影響は移動条件の計算結果であり、被災者数ではない |
| TRANSIT | 公共交通が止まると、どこへの移動が難しくなるか | 公共交通アクセス人口、Accessibility Loss、Essential Access Recovery Rate | GTFSカバレッジ外の路線は未計算または対象外と表示する |
| TRAFFIC | 自動車交通はどの経路へ移るか | 配分交通量、旅行時間、迂回距離、VKT、画面上の混雑指標 | 実測交通量の予測ではなく、モデル配分結果である |
| LOGISTICS | 物流拠点への到達性はどう変わるか | 到達時間、迂回、到達可能拠点数、影響リンク | 企業の在庫や企業間サプライチェーンは扱わない |
| RELIEF | 救援物資の輸送条件はどう変わるか | 拠点から避難所への到達時間、到達可能避難所、孤立状態の計算上の判定 | 備蓄量を根拠なく補完しない |

### 2.4 ヘッダーに常に表示する情報

利用者が地図を見ている間も、次の情報を画面上部から確認できるようにする。

- プロダクト名とStress Testであること。
- 現在のシナリオ名。
- 平常時または障害設定の別。
- 基準日または参照期間。
- データ版。
- モデル版。
- 計算状態。
- 結果の区分。
- 更新日時。

ヘッダーの情報をクリックすると、Provenanceパネルを開く。

## 3. 五段階の操作フロー

### 3.1 フロー全体

| 段階 | 利用者の問い | 画面の主目的 | 利用者が行うこと | 結果 |
|---|---|---|---|---|
| 1 | 平常時はどうなっているか | 基準状態の理解 | モードと目的地を選ぶ | 基準地図と基準指標 |
| 2 | ここを止めるとどうなるか | 障害条件の設定 | リンク、路線、港湾を選び、停止方法を指定する | シナリオ定義 |
| 3 | 何が困るか | 影響の比較 | PEOPLE、TRANSIT、TRAFFIC、LOGISTICS、RELIEFを確認する | Before / Afterと影響箇所 |
| 4 | どう戻すか | 復旧条件の比較 | リンクや路線を復旧させる | 復旧前後の改善量 |
| 5 | どこが重要か | 優先順位の検討 | Critical Linkを比較し、根拠を確認する | 影響指標別の順位と説明 |

### 3.2 平常時を見る

この段階では、利用者に障害設定を要求しない。

初期表示は、愛媛県全域の基準地図とし、画面中央に「平常時の交通ネットワークを確認する」ことを示す。

利用者は、次の順で確認する。

1. 表示モードを選ぶ。
2. 目的地カテゴリを選ぶ。
3. 地図の凡例を確認する。
4. 基準指標の計算状態を確認する。
5. 「止めてみる」へ進む。

基準指標が未計算の場合は、カードを空欄やゼロで表示しない。

「この指標は現在の公開データでは計算していません」と表示し、使用可能な別の指標またはデータ更新方法を案内する。

### 3.3 止めてみる

停止条件は、地図上の選択と一覧からの検索の両方で設定できるようにする。

地図上の細い線だけをクリック対象にすると、操作が難しくなるため、選択時には対象リンクのクリック領域を広げ、選択中の対象を一覧にも表示する。

設定できる障害条件は、次の区分で表示する。

| 対象 | 設定例 | 表示区分 |
|---|---|---|
| 道路 | 完全停止、容量50%、速度70%、車種制限 | D：ユーザー仮定 |
| 鉄道 | 路線停止、区間停止 | D：ユーザー仮定 |
| バス | 路線停止、区間影響 | D：ユーザー仮定 |
| 航路 | 航路停止 | D：ユーザー仮定 |
| 港湾 | 利用不能 | D：ユーザー仮定 |

複数の障害条件を追加できる。

追加した条件は、画面上に一覧として表示し、対象の削除、編集、復旧を可能にする。

シナリオを確定する前に、次の確認を表示する。

- 選択した対象。
- 障害の種類。
- 適用する車種または交通モード。
- 使用するネットワーク版。
- 計算できる結果。
- 計算できない結果。
- 推計または仮定であること。

### 3.4 何が困るかを確認する

影響画面では、基準状態と障害状態を同じ条件で並べる。

表示する数値には、差分の方向と単位を付ける。

たとえば、旅行時間は「42分増加」、到達可能人口は「12,400人減少」のように表示する。

「危険度」や「被害度」のような、ハザードを入力したように見える表現は使用しない。

影響画面の最初に表示する指標は、三つ以内に絞る。

- 公共交通アクセスの変化。
- 重要目的地への平均旅行時間の変化。
- 到達可能人口または物流拠点へのアクセス変化。

その下に、詳細指標と地図レイヤーを配置する。

データや計算条件が不足している場合は、カード単位で状態を表示する。

他の指標が計算済みであっても、未計算の指標を推測して埋めない。

### 3.5 どう戻すかを試す

復旧画面では、障害を取り消した場合の結果を表示する。

復旧対象は、利用者が選択したリンクまたは路線に限定する。

システムが自動的に「正しい復旧順」を決めたように見せない。

復旧候補を表示する場合は、次のように根拠を添える。

- このリンクを復旧すると、到達可能人口が何人分改善するか。
- 公共交通アクセス人口がどれだけ戻るか。
- 物流拠点への平均到達時間がどれだけ短縮するか。
- どのデータ版とモデル版で計算したか。

複数候補を比較するときは、単一の総合点だけで順位を決めない。

影響人口、公共交通、旅行時間、物流、救援物流など、指標別に並べ替えられるようにする。

### 3.6 どこが重要かを確認する

Critical Link画面では、「使えなくなった場合の影響が大きいリンク」を、指定した指標と条件に基づいて比較する。

Critical Linkは、実際の災害時に必ず優先復旧すべき道路を意味しない。

各行には、少なくとも次を表示する。

- リンクまたは路線の名称。
- 対象モード。
- 障害条件。
- 影響人口。
- 公共交通アクセスの損失。
- 旅行時間の増加。
- 貨物または救援物流への影響。
- 代替経路の有無。
- 復旧による改善量。
- データ区分。
- 計算状態。

順位の安定性を確認できる場合は、パラメータ感度の範囲とともに表示する。

感度分析を実施していない場合、モデル信頼度を数値で作成しない。

## 4. Scenario Builderの情報設計

### 4.1 初心者向けプリセット

プリセットは、作業の入口として用意する。

候補は次のとおりとする。

- 南予交通途絶チェック。
- 病院アクセスチェック。
- 主要鉄道停止チェック。
- 国道56号寸断チェック。
- 主要物流道路チェック。
- 救援物資到達性チェック。

プリセット名だけで公式被害想定だと誤解されないよう、各カードに「交通ネットワークStress Test」と表示する。

プリセットを選択した後も、対象リンク、停止条件、入力データ、結果版を確認できるようにする。

### 4.2 Expert Mode

Expert Modeでは、複数の障害、容量低下、速度低下、車種制限、対象モード、目的地、評価時間、モデルパラメータを設定する。

ただし、設定項目を表示することと、計算できることは別である。

未対応のパラメータを入力可能にする場合は、保存前に「この条件は現在の公開計算では使用されません」と表示する。

### 4.3 シナリオの保存

保存画面では、次の項目を必須とする。

- シナリオID。
- タイトル。
- 説明。
- 作成者または部署名。
- ネットワーク版。
- GTFS版。
- ODモデル版。
- 障害リンク。
- 容量低下または速度低下。
- 計算パラメータ。
- 結果版。
- 作成日時。

保存時には、結果の計算状態も保存する。

未計算シナリオを「完了」と表示しない。

最新データで再計算した場合は、新しい結果版を作成し、以前の結果を上書きしない。

## 5. 計算状態と表示ルール

### 5.1 計算状態とデータ区分を分ける

「計算状態」は、結果が利用できるかを示す。

「データ区分」は、数値がどのような根拠に基づくかを示す。

この二つを同じ色や一つのラベルにまとめない。

### 5.2 計算状態

| 状態 | 意味 | 画面表示 | 利用者ができること |
|---|---|---|---|
| computed | 入力、モデル、結果がそろっている | 計算済み | 数値、地図、説明を確認する |
| precomputed | Analysis Layerで事前計算済み | 事前計算済み | 結果を比較する |
| input_required | 必須データがない | 入力データが必要 | 不足データと取得条件を確認する |
| not_computed | 計算器または公開結果が未提供 | 未計算 | 未計算理由と実装予定を確認する |
| blocked_by_license | 利用条件が未確認または公開不可 | 利用条件確認中 | 公開できない理由を確認する |
| stale | データまたは結果が運用基準より古い | 旧版の結果 | 最新版での再計算を要求する |
| validation_failed | 入力検証に失敗した | 検証失敗 | エラー箇所を確認し、更新を差し戻す |
| unsupported | 入力範囲または形式が対象外 | 対象外 | 対象範囲と代替手段を確認する |
| failed | 計算処理が異常終了した | 計算エラー | エラーIDを管理者へ伝える |
| preview_only | 管理者の候補版を確認中 | プレビュー | 承認前の候補として確認する |

### 5.3 状態ごとの表示文

状態をアイコンや色だけで示さない。

画面には、状態名、理由、結果の扱い、次の操作を文章で表示する。

| 状態 | 表示文の例 |
|---|---|
| computed | 計算済み。使用データとモデル条件を確認できます。 |
| input_required | この指標の計算に必要なGTFS入力がありません。推計値やゼロ値で補完していません。 |
| not_computed | このシナリオの交通量再配分はまだ計算していません。現在表示できるのは事前計算済み結果です。 |
| blocked_by_license | 利用条件を確認できないデータを公開用結果に使用していません。 |
| stale | 表示中の結果は旧データ版で作成されています。最新データで再計算するまで、現行値として扱わないでください。 |
| validation_failed | 更新データの検証に失敗しました。active版は変更されていません。 |
| failed | 計算に失敗しました。エラーIDと入力版を記録し、管理者に連絡してください。 |

未計算状態で「影響なし」と表示しない。

データがない場合の表示は、ゼロ値、空の地図、成功メッセージで代用しない。

### 5.4 データ区分

結果の根拠は、次のラベルを文章で表示する。

| 区分 | ラベル | 表示の意味 |
|---|---|---|
| A | 公式観測および実績 | 公開された観測値または実績統計そのもの |
| B | 公式統計加工 | 公式データを空間対応付け、集計、変換した値 |
| C | モデル推計 | Gravity Model、IPF、交通量配分、アクセシビリティ等の計算値 |
| D | ユーザー仮定 | 停止、容量低下、速度低下、路線運休等の設定値 |

区分ラベルは、凡例、指標カード、詳細パネル、ダウンロード可能な結果メタデータに付ける。

## 6. Provenanceと説明可能性

### 6.1 詳細パネルの必須項目

結果または地図上の対象を選択すると、次の情報を確認できるようにする。

- 使用データセット名。
- データ版。
- 出典。
- ライセンス。
- 基準日または参照期間。
- 取得日。
- 入力データの区分。
- モデル名。
- モデル版。
- パラメータ。
- シナリオの障害条件。
- 影響リンク。
- 影響ゾーン。
- 計算日時。
- Gitのコミット識別子。
- 制約と未計算範囲。

### 6.2 説明の三段階

説明パネルは、利用者の目的に応じて三段階に分ける。

1. 結論：設定した条件で、何がどれだけ変化したか。
2. 根拠：どのデータ、モデル、パラメータを使ったか。
3. 詳細：入力版、変換、計算式、検証値、制約を確認する。

最初から詳細な技術情報を全面表示しない。

ただし、詳細を隠して数値だけを見せることも避ける。

### 6.3 Coverage表示

データが県全域をカバーしていない場合、地図上でカバレッジを表示する。

カバレッジ外を「交通がない地域」または「到達不能」と解釈できる表示にしない。

カバレッジ外の例は、次のとおりである。

- GTFSが提供されていない事業者。
- 鉄道の時刻表データが未確認の路線。
- 港湾または物流施設の位置情報が未確認の拠点。
- 道路交通センサスとの対応付けができないリンク。

## 7. Data Update Centerの情報設計

### 7.1 利用境界

Data Update Centerは、公開用Public Layerに含めない。

認証された管理者環境で起動し、候補版、検証結果、承認履歴、ロールバック履歴を管理する。

GitHub Pagesの画面から、直接ファイルをアップロードしたり、active版を変更したりしない。

### 7.2 役割

| 役割 | 主な責任 | できる操作 |
|---|---|---|
| データ担当 | 出典、基準日、データ内容を確認する | アップロード、メタデータ入力、プレビュー |
| 検証担当 | Validationと差分を確認する | 検証結果確認、差し戻し |
| 承認者 | 公開条件と業務上の妥当性を確認する | active切替、承認取消 |
| システム保守担当 | 失敗復旧と再現性を維持する | rollback、ログ確認、再ビルド |

同一人が入力からactive切替までを単独で完了できない運用を基本とする。

小規模な運用で役割を兼務する場合も、入力者、承認者、実行日時を監査ログに残す。

### 7.3 更新フロー

Data Update Centerの画面は、次の六段階で構成する。

1. アップロード。
2. 形式確認と自動Validation。
3. 旧active版との差分確認。
4. プレビュー。
5. 承認。
6. active切替と公開bundle再生成。

各段階で、利用者が次に何を確認すべきかを画面上に示す。

### 7.4 アップロード

最初の画面では、ファイルだけでなく、次のメタデータを入力させる。

- dataset_id。
- データセット名。
- 提供者。
- 出典URL。
- ライセンス。
- 基準日。
- 取得日。
- 更新頻度。
- 対象地域。
- 想定する利用目的。
- 既存active版との関係。

対応形式は、GTFS ZIP、CSV、XLSX、GeoJSON、Shapefile ZIP、GeoPackageとする。

ライセンスが不明な場合は、candidateとして保持できるが、公開用active版には切り替えない。

### 7.5 自動Validation

検証結果は、成功または失敗だけでなく、警告と確認事項を分けて表示する。

共通検証は次のとおりである。

- ファイル形式。
- MIMEと拡張子の整合性。
- ファイルサイズ。
- checksum。
- ZIPのパス逸脱。
- ZIPの展開後サイズ。
- 必須列または必須ファイル。
- 文字コード。
- null。
- 重複ID。
- 参照整合性。
- CRS。
- geometry。
- 個人情報または非公開情報の混入。
- ライセンスと出典の記載。

GTFSでは、agency、stops、routes、trips、stop_times、calendar、calendar_datesを対象に、ID整合性、時刻、サービス日、重複、停留所座標、形状の有無を確認する。

GISでは、geometryの妥当性、座標範囲、CRS、自己交差、空間範囲、属性IDを確認する。

XLSXやCSVでは、列名、データ型、日付、数値、重複、欠損、基準日を確認する。

検証失敗版はactive版に切り替えない。

### 7.6 差分確認

旧active版と候補版の差分は、件数だけでなく、業務上の変更内容として表示する。

- 追加。
- 削除。
- 属性変更。
- 座標変更。
- 基準日変更。
- データ範囲変更。
- ライセンスまたは出典変更。
- スキーマ変更。

削除件数が大きい場合や、座標が大きく変化した場合は、承認者の確認を必須とする。

差分が取れない場合は、差分なしと表示しない。

「比較不能」と理由を表示し、候補版を承認保留にする。

### 7.7 プレビュー

プレビューでは、候補版の地図、表、件数、警告、出典、ライセンスを確認する。

候補版を見ていることが分かるよう、画面全体に「公開前の候補版」と表示する。

プレビュー結果を公開版のデータと混同しない。

### 7.8 承認とactive切替

承認者は、次の確認項目を埋めてからactive切替を行う。

- 出典URLを確認した。
- ライセンス条件を確認した。
- 必須検証が成功した。
- 警告を確認した。
- 旧版との差分を確認した。
- Public Layerに公開できるデータだけが含まれている。
- Phase Bの許諾未確認データが含まれていない。
- 旧版へrollbackできる。

active切替は、旧版を削除せず、旧版のstatusをarchivedへ変更する。

公開bundleの再生成に失敗した場合は、active版を切り替えたように見せず、再ビルド待ちとして停止する。

### 7.9 Rollback

rollbackは、旧版の削除ではなく、指定したarchived版をactiveとして再指定する。

rollback時には、次の情報を記録する。

- 対象dataset_id。
- 切替前の版。
- 切替後の版。
- 実行者。
- 実行日時。
- 理由。
- 影響する公開bundle。
- 再計算が必要なシナリオ。

過去のシナリオ結果は削除しない。

過去結果と最新データによる再計算結果は、result_versionで区別する。

## 8. アクセシビリティ設計

### 8.1 目標

設計目標は、WCAG 2.2 AA相当の操作可能性、知覚可能性、理解可能性、堅牢性である。

地図を利用できない環境でも、主要な結論、対象一覧、計算状態、出典を確認できるようにする。

### 8.2 キーボード操作

次の操作をキーボードだけで完了できるようにする。

- 五段階フローの移動。
- モード選択。
- シナリオプリセットの選択。
- 障害条件の追加、編集、削除。
- 結果カードの展開。
- Provenanceパネルの開閉。
- Data Update Centerの入力、差分確認、承認操作。

地図上のリンク選択をキーボードで実現できない場合は、同じ対象を検索または一覧選択できる代替経路を用意する。

フォーカス位置を視認できるようにする。

モーダルを閉じた後は、開く操作を行った要素へフォーカスを戻す。

### 8.3 色とコントラスト

区分や状態を色だけで区別しない。

ラベル、アイコン、パターン、線種、文章を組み合わせる。

地図上の色が識別できない場合も、一覧と詳細パネルで対象を確認できるようにする。

テキストと操作要素は十分なコントラストを確保し、背景地図上に直接長文を重ねない。

### 8.4 スクリーンリーダーと代替表示

地図には、地図の目的、表示レイヤー、選択対象、現在のシナリオを説明する代替テキストを付ける。

地図で選択した対象は、表形式またはリスト形式でも確認できるようにする。

Before / Afterは、色の変化だけでなく、数値と増減語で表現する。

動的に更新される結果は、更新内容を適切なライブ領域で通知する。

### 8.5 モバイルと表示密度

スマートフォンでは、地図と指標を同時に詰め込まず、地図、指標、説明を縦方向に並べる。

横スクロールを前提にした表を避け、重要列を先に表示する。

デスクトップでは、地図と結果パネルを並べて比較できるようにする。

端末の幅が狭くても、シナリオ名、計算状態、増減、出典への入口を常に確認できるようにする。

### 8.6 読みやすい日本語

行政実務で使う表現を優先し、略語は初出時に説明する。

例として、GTFSは「公共交通の停留所、路線、便、時刻を表す標準データ」と説明する。

エラー表示は、技術的な例外名だけで終わらせず、利用者が取るべき行動を示す。

## 9. 引継ぎと継続運用

### 9.1 引継ぎに必要な成果物

担当者が交代しても運用できるよう、次の成果物を一つの運用フォルダまたはリポジトリから参照できるようにする。

- 操作マニュアル。
- データ更新手順。
- データインベントリ。
- ライセンス一覧。
- 現在のactive版一覧。
- Validation結果。
- 差分確認結果。
- 承認履歴。
- rollback手順。
- シナリオ保存形式。
- モデル方法書。
- 検証結果。
- 既知の制約。
- 障害時の連絡先。
- GitHub ActionsとPagesの状態確認方法。

### 9.2 新任担当者が最初に確認する項目

新任担当者は、次の作業を順番に行える必要がある。

1. 現在のactiveデータ版を確認する。
2. データの出典とライセンスを確認する。
3. 公開画面で計算済みと未計算の指標を見分ける。
4. プリセットを一つ開き、障害条件と結果版を確認する。
5. Provenanceから使用データとモデルを確認する。
6. candidate版をactiveにせず、Validationと差分を確認する。
7. 承認前の候補版を差し戻す。
8. 必要な場合に旧版へrollbackする。
9. rollback後に影響する公開bundleとシナリオを確認する。

この一連の作業を、特定の開発者の記憶や口頭説明だけに依存させない。

### 9.3 運用上の禁止事項

- active版の直接上書き。
- ライセンス不明データの公開。
- ODPT等の認証情報のリポジトリ保存。
- Phase Bデータの加工または派生レイヤー公開。
- 未計算結果をゼロまたは「影響なし」と表示すること。
- Synthetic ODを実測ODと表示すること。
- 旧結果を新データで上書きすること。
- 管理画面をPublic Layerへ公開すること。

## 10. A0で確定する設計とA1への入力

### 10.1 A0で確定すること

- Public Layerは、五段階の利用フローを中心にする。
- PEOPLE、TRANSIT、TRAFFIC、LOGISTICS、RELIEFは同一シナリオで切り替える。
- 計算状態とデータ区分を分離して表示する。
- 未計算、入力不足、ライセンス保留、旧版、検証失敗を別状態として扱う。
- 地図を使えない利用者向けに、一覧、表、説明パネルを用意する。
- Data Update Centerは認証された管理者環境に分離する。
- 更新は候補版、Validation、差分、プレビュー、承認、active切替の順に進める。
- 旧版を保持し、rollbackと結果版の追跡を可能にする。
- A0では完成版UIを実装しない。

### 10.2 A1で実装前に確認する条件

A1でPublic Layerを実装する前に、次を確認する。

- GTFSの対象事業者、取得条件、期間、カバレッジ。
- 道路ネットワークの公開範囲と属性。
- 人口および目的地データの公開条件。
- 計算可能な指標と未計算にする指標。
- 事前計算結果のファイルサイズ。
- 県全域表示と松山都市圏重点表示の切替方法。
- 公開用データに付与するProvenanceの形式。
- キーボード操作と地図代替表示のテスト方法。
- Data Update Centerの承認権限と監査ログの保存場所。

A1の開始条件が満たされない指標は、UIを先に作って存在するように見せない。

## 11. A0の受入基準

本書は、次の条件を満たしたときA0のUX成果物として受け入れる。

- 五段階の利用フローを画面構成に対応付けている。
- 五つの表示モードの目的と制約を定義している。
- 計算済み、未計算、入力不足、ライセンス保留、旧版、検証失敗を区別している。
- 公式値、加工値、モデル推計値、ユーザー仮定を画面で区別する方針がある。
- Data Update Centerのアップロードからrollbackまでを定義している。
- 直接上書きと公開前候補版のactive化を禁止している。
- 地図を使わない代替表示とキーボード操作を定義している。
- 新任担当者への引継ぎに必要な成果物を定義している。
- Phase Bの地震被害想定GISをUX設計の入力データとして扱っていない。
- A1以降の実装課題を明確にしている。
